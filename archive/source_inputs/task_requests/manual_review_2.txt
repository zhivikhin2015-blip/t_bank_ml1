### 1. Сохрани исходный протокол

- 500 клиентов и 50 активов, выбранных по истории до первого прогноза.
- Существующие временные границы train / validation / test.

### 2. Усиль сравнение baseline

Сохрани существующие методы и добавь три правила ранжирования:

1. По популярности актива за предыдущий месяц.
2. По числу покупок актива клиентом за предыдущие три месяца.
3. Сначала по числу покупок актива клиентом за предыдущие три месяца, при равенстве — по популярности актива за предыдущий месяц.

Для третьего правила используй явную сортировку по двум критериям, без искусственного большого множителя.

Все методы должны использовать одинаковые пары и ответы. Используй единый воспроизводимый порядок разрешения равенств, привязанный к ключу `(customerID, prediction_date, ISIN)` и seed. Он не должен зависеть от текущего порядка строк.

Эти правила дают ранжирование, а не вероятности. Для них показывай Recall@5, Precision@5 и NDCG@5; LogLoss и ROC-AUC оставь пропусками. Для вероятностных методов сохрани LogLoss и ROC-AUC наряду с метриками ранжирования.

### 3. Сделай сравнение признаков прозрачным

В итоговую таблицу включи:

Здесь 100/7 означает `max_iter=100`, `max_leaf_nodes=7`.

Сохрани исходные четыре настройки и исходное правило выбора: выше Recall@5, затем ниже LogLoss, затем меньше итераций и листьев.

Заново определи победителя по этому правилу. Ожидаемый результат — 200/7, но не фиксируй его принудительно и не подгоняй вычисления. Если победитель изменится, проверь воспроизводимость и объясни причину. Дополнительные диагностики не должны менять правило выбора.

Отдельно сравни:

- пользу добавления признаков при одинаковых настройках 100/7;
- эффект выбора настроек при неизменных пяти признаках.

### 4. Расширь оценку на validation

Рассчитай итоговые и помесячные метрики для всех методов:

- Recall@5;
- Precision@5;
- NDCG@5;
- LogLoss и ROC-AUC — только для вероятностных методов.

Зафиксируй определения:

- Основные метрики ранжирования — средние по случаям «клиент — месяц» с хотя бы одной покупкой внутри каталога из 50 активов.
- Recall@5 внутри случая — число купленных активов в top-5, делённое на число всех купленных активов внутри каталога.
- Precision@5 внутри случая — число купленных активов в top-5, делённое на пять.
- NDCG@5 — с бинарной релевантностью, скидкой `1 / log2(rank + 1)` и идеальным DCG, рассчитанным по числу положительных активов внутри каталога.
- Месяцы без покупок внутри каталога исключаются из основных средних метрик ранжирования.
- Дополнительно покажи Precision@5 по всем случаям «клиент — месяц», включая месяцы без покупок. Назови эту метрику отдельно.
- LogLoss и ROC-AUC считаются по всем кандидатным парам. Если ROC-AUC для какого-либо среза не определён из-за наличия только одного класса, показывай пропуск с пояснением.

Для общего validation и каждого месяца покажи:

- число кандидатных пар и положительных пар;
- общее число случаев «клиент — месяц»;
- число случаев, включённых в основные метрики ранжирования;
- число уникальных клиентов, включённых в эти метрики.

Итоговые средние считай непосредственно по всем учитываемым случаям validation, а не как невзвешенное среднее шести месячных значений.

### 5. Покажи ограничения каталога и диагностику покупок

**Покрытие каталога**

Считай долю уникальных покупок выбранных клиентов, покрытую каталогом:

- числитель — число уникальных троек `(customerID, ISIN, prediction_date)` с покупкой внутри выбранных 50 активов;
- знаменатель — число таких троек со всеми купленными активами выбранных клиентов за целевые validation-месяцы.

Повторные сделки одной пары внутри целевого месяца дают одну уникальную покупку. Покажи покрытие за весь validation и по месяцам. Не используй test.

**Новые и повторные покупки**

Заранее зафиксируй определение:

- повторная покупка — положительная пара, для которой была хотя бы одна покупка в предыдущие три календарных месяца строго до даты прогноза;
- новая покупка — положительная пара без покупки в этом окне.

Подчеркни, что «новая» здесь не означает первую покупку за всю жизнь клиента.

Для каждого метода оцени Recall@5 отдельно для этих двух групп:

- используй исходный top-5 метода;
- не перестраивай рекомендации после фильтрации по будущим ответам или группе;
- внутри случая дели число найденных положительных активов соответствующей группы на число всех положительных активов этой группы внутри каталога;
- усредняй только по случаям с хотя бы одним положительным активом соответствующей группы;
- покажи число положительных пар, учитываемых случаев и уникальных клиентов для каждой группы.

### 6. Оцени устойчивость различий

Добавь воспроизводимый парный bootstrap по клиентам:

- seed зафиксируй явно;
- число повторов — 5000;
- выбирай с возвращением из всех 500 клиентов;
- при выборе клиента сохраняй все его validation-месяцы и учитывай кратность выбора;
- для сравниваемых методов используй одинаковые bootstrap-выборки;
- в каждой выборке пересчитывай средний Recall@5 по учитываемым случаям «клиент — месяц», а не усредняй предварительно рассчитанные средние клиентов;
- явно обработай выборку без учитываемых случаев, если такая возникнет.

Рассчитай точечную разницу и 95%-й процентильный интервал разницы Recall@5:

1. Выбранная модель минус правило «покупки пары за три месяца, затем популярность».
2. Выбранная модель минус бустинг с пятью признаками и настройками 100/7.

Пометь интервалы как диагностические: подбор модели на том же validation не позволяет считать их независимым подтверждением преимущества. Не утверждай устойчивое преимущество, если интервал включает ноль.
